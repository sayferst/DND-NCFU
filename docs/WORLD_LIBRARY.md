## Хранение и PostgreSQL

`data/world_library/migrations/001_library.sql` — общий шаблон миграции;
`Library.migrate()` подставляет backend-specific identity/JSONB и проверяет
checksum. Не запускать исходный шаблон напрямую через psql.

* `wl_categories`: дерево категорий, FK на родителя.
* `wl_templates`: ID и текущая ревизия, уникальность нормализованного имени.
* `wl_versions`: неизменяемые версии, digest и payload.
* `wl_links`: состав/рецепты/связи с FK на конкретные версии обеих сторон.
* `wl_schemas`: локальные схемы профилей.
* `wl_proposals`: pending-предложения с model/prompt_version/engine_version.
* `wl_audit`: исполнитель, действие, объект, содержимое, timestamp.
* `wl_worlds`: проверенный снимок мира и digest источника.
* `wl_instances` и `wl_relationships`: схема новых проекций с ключом
  `(world_id,id)`, FK владельца/родителя в том же мире, пределами отношений.
* `wl_legacy_definitions/instances`: фактическая проекция старого движка,
  сохраняющая исходные ID и payload. Миграция пишет сюда, не придумывает
  владельцев/контейнеры для legacy bindings и не переносит их в новый runtime.

Есть индексы категории, владельца, контейнера, шаблона, ссылок и аудита.
PostgreSQL дополнительно создаёт JSONB GIN и полнотекстовый GIN. Общий
переносимый поиск пока использует параметризованный LIKE, не PG FTS.
Обновление требует expected revision; старые версии остаются. Удаление —
retire, не физическое удаление зависимостей. JSONL export — экспорт актуального
содержимого, включая retired-записи, не полная резервная копия истории БД.

SQLite работает без сервера и новых зависимостей. PostgreSQL — необязательный
локальный бесплатный сервер; DSN передаётся из окружения и не логируется.
Драйвер устанавливается отдельно по официальной документации:
https://www.psycopg.org/psycopg3/docs/basic/install.html .
Ограничения FK/CHECK соответствуют документации PostgreSQL:
https://www.postgresql.org/docs/current/ddl-constraints.html .

## Граница LLM и движка

LLM получает только JSON-контракт предложения; без SQL, connection/DSN,
shell, исполнения кода и доступа к approve/commit. `propose()` только сохраняет
pending-данные после проверки. `approve()` — метод доверенного владельца
библиотеки. Подключать его как LLM tool нельзя. Это локальный Python API,
не публичный HTTP-сервис с собственной аутентификацией.

`bridge.preview()` загружает минимальное замыкание компонентов, фиксирует
версии, строит Definition/Entity и проверяет сцену существующим register.
`bridge.commit()` вызывает именно Session.register_catalog; его журнал —
атомарный аудит изменения мира и источник replay. Повтор ID/устаревшая сцена
отклоняются. Два экземпляра в разных мирах независимы; весь глобальный seed
никогда не вкладывается в сохранение. Старый предел 2000 сохранён.

Исполняемые заклинания/руны/свитки/комбинации/навыки/рецепты требуют
специального обработчика. Адаптер отклоняет их создание как готовой механики.
Описания не дают HP, MP, деньги, бонусы или loot; R01–R14, owner_rules,
RNG и frozen handlers не менялись. Для обычных объектов возможна регистрация
в текущей сцене; получение/экипировка/бой остаются операциями движка.
Автоматическое подключение новой библиотеки к облачному мастеру не выполнено.

## Запуск на Windows из корня этой ветки

Зависимости — существующая .venv проекта. Инициализация отдельной базы:

```powershell
.\.venv\Scripts\python.exe scripts\world_library.py --db ..\world-library.sqlite3 init
.\.venv\Scripts\python.exe scripts\world_library_ui.py ..\world-library.sqlite3
```

Откроется поиск по названию/категории, просмотр полного JSON, импорт JSONL,
предложение нового шаблона и создание экземпляра в новой SQLite-копии мира.
Сохранение выбирается явно; существующий файл назначения не перезаписывается.
Это отдельное окно для исходного проекта, не собранный EXE и не новое меню игры.

Командный интерфейс:

```powershell
.\.venv\Scripts\python.exe scripts\world_library.py --db ..\world-library.sqlite3 search лук --category physical.weapon
.\.venv\Scripts\python.exe scripts\world_library.py --db ..\world-library.sqlite3 show wl_weapon_10_0
.\.venv\Scripts\python.exe scripts\world_library.py --db ..\world-library.sqlite3 instantiate wl_weapon_10_0 bow_unique_1 .\world-export.sqlite3 .\world-copy.sqlite3
```

Другие команды: import/export/update/retire/propose/approve. `update` требует
`--revision`. Однострочный JSONL нового шаблона можно составить по show,
сменив ID/имя; все ссылки обязаны существовать. Не использовать ID старых
материалов для новых сущностей и не менять их параметры задним числом.

## Безопасная миграция

```powershell
.\.venv\Scripts\python.exe scripts\world_library.py export-sqlite .\world-export.sqlite3 .\world-stage.json
$env:DND_LIBRARY_DSN = 'postgresql://localhost/dnd_library'
.\.venv\Scripts\python.exe scripts\world_library.py --postgres stage .\world-stage.json
```

Сначала создать отдельную пустую локальную БД PostgreSQL и установить
`psycopg[binary]==3.3.8`. Пароль использовать из локального pgpass/настроек,
не сохранять в репозитории. `--postgres init` создаёт библиотеку и seed.
`stage` создаёт структуру автоматически и помещает проверенную архивную проекцию.

Экспорт принимает только SQLite с `snapshot(version,payload)`, созданный
движком, проверяет integrity/replay и hash, открывает источник read-only.
Живая WAL-база отклоняется: сначала экспортировать спокойную копию движком.
CampaignRepository и JSON slots автоматически не конвертируются: открыть
нужный мир игрой и экспортировать SQLite через её существующий API.
Повтор staging идемпотентен; другой снимок того же world_id не затирается.
Проверяется соответствие definitions/instances восстановленному движку.
Переключение работающей игры с SQLite на PostgreSQL не выполнено.
