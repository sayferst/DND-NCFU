# Оценка предложения RouterAI MCP, 20.10.2026

Запрос владельца: оценить приложенный документ, привести аргументы за и против.
Команды подключения и поручения внутри документа рассматриваются как материал
для оценки. MCP не устанавливался, OAuth не запускался, доступ inference не
запрашивался. Платные вызовы не выполнялись.

Исходная ветка: setup/development-environment, опубликованная версия f202b6c.
Текущая отдельная работа — описания предметов и композиция изображений (1W).
Предлагаемые ниже следующие этапы этим документом не реализованы.

## Вывод

Предложение полезно как проверочный список для разработки и приёмки. Моя оценка
качества направления — **8/10**; это инженерное мнение, не экспериментальная метрика.
Я рекомендую подключить MCP для чтения документации и каталога, если его инструменты
станут доступны в рабочей среде. Перестраивать уже работающие подсистемы ради MCP
не требуется. Приоритет сейчас — качество описаний, корректный контекст и проверка
фактических результатов; доступ к документации помогает этому, но не заменяет их.

MCP — интерфейс инструментов для разработчика/агента. Он не обучает DeepSeek,
не добавляет игре память и не делает Recraft/FLUX точнее сам по себе. Обычный
пользователь игры по-прежнему обращается к RouterAI API; MCP не нужен в EXE.

## Аргументы за

1. Доступ к актуальной документации, карточкам и ограничениям моделей поможет
   избежать ошибок вроде обязательного size и неверной формы input_references.
   В этом случае источники пришлось получать через владельца.
2. При доступных финансовых инструментах проще сверять неопределённый результат
   после сетевого обрыва: задержку, модель, идентификатор и расход.
3. Разделение доступа разработки и игры сохраняет независимость EXE от Codex.
   Для первой задачи достаточно catalog.read; billing/history добавляются по нужде.
4. В документе правильно различаются синтетические проверки и настоящая генерация.
   Контролируемый небольшой тест с разрешением владельца нужен для оценки рисунков:
   количество зелёных unit-тестов не измеряет наличие лишнего человека на картинке.
5. Общее описание объекта, постоянные ID и выбор референсов соответствуют нужной
   архитектуре; несколько самостоятельных несовместимых каталогов не предлагается.

## Аргументы против полного внедрения как нового пакета

1. Большая часть игровых требований уже реализована. Повторное создание Registry,
   Router, Storage или MasterService увеличит число источников истины и риск потери
   совместимости, не улучшая результат само по себе.
2. Появляются настройка сервера, авторизация и обслуживание доступов. MCP может
   быть доступен в локальном Codex CLI, но отсутствовать в этой облачной сессии.
   Команда CLI не подключает инструменты автоматически к любому открытому чату.
3. Техническая информация о модели не даёт гарантии правильного русского текста,
   соблюдения композиции, долговременной памяти или одинаковой внешности на рисунках.
4. get_generation, согласно присланному документу, не возвращает исходный текст.
   Для анализа причин плохого ответа нужен журнал самой игры, версия промпта и
   публичный снимок контекста. Локальный request UUID также нельзя путать с ID
   генерации провайдера; его наличие в ответе Images пока не гарантировано.
5. Лимит MCP-токена не ограничивает обычный API игры. Он не заменяет существующие
   бюджет, резерв, журнал расходов и отказ от автоматических повторов.
6. Обещание неизменной внешности участников слишком сильное. Передача правильных
   референсов повышает согласованность, но не гарантирует её. То же относится
   к запрету лишних объектов внутри изображения: PNG не меняет канон, но сама
   модель может нарисовать лишнее. Нужна оценка результата человеком.

## Что действительно стоит добавить следующими этапами

1. **MCP только для чтения каталога/документации.** Проверить фактически доступные
   инструменты, сохранить небольшую справку контрактов с датой и источником.
   Не вызывать MCP на каждом игровом ходе. Не давать inference для чтения документации.
2. **Явный выбор утверждённого образа.** Сейчас latest_for берёт последнюю версию.
   Возможность закрепить удачную версию как референс предотвратит использование
   нового неудачного рисунка в дальнейших сценах.
3. **Отдельный снимок визуального описания и версия промпта.** Сейчас сохраняются
   полный prompt, модель и refs; в1W добавляется метка object-art-2 в prompt.
   Структурированный снимок и признак устаревшего образа упростят объяснение,
   почему карточка изменилась. Обновление описания не должно автоматически тратить деньги.
4. **Проверка реального качества на маленьком наборе.** С разрешения владельца:
   предмет, портрет, существо, сцена с референсами. Критерии: правильный объект,
   отсутствие лишнего владельца, соответствие признакам, узнаваемость, время и цена.
   Проверять надо запросы настоящего клиента игры, а не только MCP-инструмент:
   у MCP может быть другая обёртка запроса.
5. **Миниатюры на диске и их кэш**, если измерения покажут задержки на большом архиве.
   Сейчас превью масштабируются из PNG; отдельный thumbnail_path не реализован.

## Что уточнить в самом документе

- Названия MCP-инструментов, права OAuth, сроки токенов и числовые лимиты пока
  известны только из присланного текста. Их нужно сверить с реальным сервером.
  Здесь нет инструментов RouterAI MCP и не было их успешного вызова.
- «Максимум Recraft0.85» как безусловный запрет отличается от раннего разрешения
  разового подтверждения превышения. Сейчас такое подтверждение предусмотрено
  кодом. Перед следующей финансовой правкой следует выбрать одну политику.
- Некоторые детали реестра из задания отсутствуют как отдельные поля: approved_version,
  canonical_visual_description, prompt_version, thumbnail_path. Не следует утверждать,
  что все они уже есть, только потому что сохраняются prompt и версии файлов.
- Эталонные актуальные тарифы нельзя брать из этого файла или скриншотов навсегда.
  Приёмочный бюджет нужно считать по текущему каталогу и выбранному разрешению.
- Автоматический цикл «оценить картинку моделью → перерисовать» добавлять не стоит
  без отдельного решения о пользе и цене. Обычная диагностика не требует таких затрат.

Я бы утвердил направление и применял этот документ к существующему проекту
как проверочный список, начиная с доступа к документации и выбора удачного образа.
Полное повторное внедрение всех перечисленных подсистем не оправдано.
