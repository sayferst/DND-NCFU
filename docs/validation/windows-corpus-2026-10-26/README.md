Подтверждены четыре ошибки чтения UTF-8 как cp1251 и один ZIP-случай;

Две соответствующие платформенные проблемы отдельно воспроизведены в Linux:

1. Чтение UTF-8 JSONL без encoding использует Windows cp1251. С настоящим
   UTF-8 экспортом это вызывает UnicodeDecodeError. Регрессия подменяет только
   неуказанную кодировку Path.open на cp1251 и запускает тот же тест экспорта.
2. ZipInfo на Windows нормализует обратный слеш в filename. Исходный spelling
   остаётся в orig_filename, но прежний валидатор проверял только filename.
   Регрессия моделирует именно это поведение стандартного zipfile и проверяет
   настоящий ZIP, без извлечения/исполнения содержимого.

reproduce-01.txt:9passed/2failed до исправления. Это реальная воспроизводимая
ошибка, а не предположение о завершении нативного Windows-прогона.

Исправлено:
- Явный UTF-8 в чтении нового экспорта, резервных копий/старых fixtures/метаданных
  тестов и настройки RAG. Байты существующих файлов не переписываются.
- Проверяется orig_filename и отклоняется любое изменение имени библиотекой,
  включая обратный слеш и NUL. Существующие запреты traversal/drive/symlink
  и отсутствие извлечения сохранены.
- Тестовый ZIP сохраняет недопустимое имя в самом заголовке; прежний удобный
  writestr(name, ...) на Windows заранее превращал проверяемое имя в допустимое.
  Добавлен отдельный NUL-случай и две платформенные регрессии.
