# Восстановление ngrok после неудачного self-update

Владелец подтвердил на Windows f3bb8b3:12207passed/1skipped, Ruff check/format
384файла успешны. Отдельная неисправность хоста: после update с кодом0 в
управляемой папке оставался только .ngrok.exe.old, а PATH выбирал WinGet3.3.1.
Повтор той же команды воспроизводил отсутствие установленного ngrok.exe.

Обновление теперь выполняется во временной копии в папке хоста. Только после
успешной проверки минимальной версии новый EXE атомарно заменяет установленный.
Используется прямая загрузка официального Windows AMD64 ZIP. Команда self-update
полностью исключена, установленный агент/WinGet не запускается при обновлении:
https://bin.equinox.io/c/bNyj1mQVY4c/ngrok-v3-stable-windows-amd64.zip

Загрузка ограничена40МиБ, EXE100МиБ; извлекается ровно ngrok.exe, без extractall.
Перед запуском загруженного файла Windows проверяет Authenticode Status=Valid
и точное имя издателя ngrok, Inc. При отказе загрузки/подписи/версии прежний
установленный файл сохраняется. Существующий .ngrok.exe.old и конфигурация
хоста не трогаются. Ключи не читаются, NGROK_AUTHTOKEN/API_KEY исключаются
из среды subprocess. Пробник версии использует явный UTF-8.

Linux:64целевых теста прошли, включая точный сценарий «update0 → EXE исчез»,
повреждённую загрузку/подпись, защиту установленного файла и прежней .old.
Тесты подписи и обновления в Linux используют заглушки, не считаются native QA.
Отдельный workflow Native ngrok recovery на Windows скачивает официальный
архив, проверяет настоящую подпись и запускает только version; туннель,
модельные API, ключи, пользовательские настройки не используются.

После получения исправления: UPDATE_NGROK.bat, затем START_HOST.bat.
Общий игровой набор/Setup из-за этого исправления хостового инструмента
вручную повторно запускать не требуется. Новых платных запросов0.

скачан, допущен проверкой Windows Authenticode/издателя и выполнил version.

Запуск реального хоста владельца после обновления проверяет владелец.

официальный загрузчик, затем version и os.replace. Linux65passed, Ruff успешны.

не к этой новой проверке всего обновления.

После HTTP200 в однобайтовой пробе владельца добавлен резервный системный
Windows HTTPS для ошибок полной Python-загрузки. Он использует системные
прокси/доверенные CA, скачивает блоками64КиБ с пределом40МиБ и ограниченным
временем. TLS-проверка не отключается, финальный URI должен оставаться HTTPS.
Подпись/издатель/версия проверяются перед установкой по прежним правилам.
Повреждённый ZIP или неверная подпись не обходятся резервным транспортом.
