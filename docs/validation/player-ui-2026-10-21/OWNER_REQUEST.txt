# DND-NCFU — Масштабное обновление интерфейса, режим разработчика и подготовка игры к закрытому тестированию

## 1. Основная цель

Необходимо переработать пользовательский интерфейс DND-NCFU, отделить функции разработчика от обычного игрового процесса и подготовить приложение к передаче другим пользователям через Windows-установщик.

Игра уже обладает работающими системами:

- генерация персонажей;
- генерация миров;
- текстовый ИИ-мастер;
- постоянная память кампаний;
- игровой журнал;
- «Хроники мира»;
- генерация изображений через RouterAI;
- сохранение иллюстраций;
- создание сюжетных сцен;
- Windows EXE-сборка.

Нельзя разрушать существующую функциональность.

Цель — превратить текущий рабочий прототип в привлекательную и удобную фэнтезийную RPG, которую можно установить и начать проходить без необходимости разбираться в технических настройках нейросетей.

Разработка должна затронуть интерфейс, навигацию, безопасность API, разделение пользовательских ролей, галерею изображений, анимации и дистрибуцию.

**Ключевое требование: игрок должен заниматься приключением, а не настройкой программного обеспечения.**

# ЧАСТЬ I. ДВА РЕЖИМА ПРИЛОЖЕНИЯ

## 3. Режим обычного игрока

Это основной режим, который автоматически открывается после установки игры.

В нём должны быть доступны:

1. Главное меню.
2. Новое приключение.
3. Продолжение приключения.
4. Создание персонажа.
5. Создание нового мира.
6. Игровой журнал.
7. Диалоги с NPC.
8. Инвентарь.
9. Характеристики героя.
10. Карта и доступные игровые локации, если реализованы.
11. Энциклопедия мира.
12. Фотоальбом приключения.
13. Создание изображений доступных объектов.
14. Визуализация сюжетных событий.
15. Обычные пользовательские настройки.
16. Сохранение и загрузка.

При этом игрок не должен видеть техническую реализацию нейросетей.

Убрать из обычного режима прямой доступ к:

- настройкам модели DeepSeek;
- выбору провайдера LLM;
- API-ключам;
- настройкам подключения Recraft;
- настройкам подключения FLUX;
- техническим промптам;
- отладочным ответам моделей;
- параметрам контекста;
- внутренним лимитам запросов;
- диагностическим инструментам разработчика;
- переключателям внутренней архитектуры игры.

Оставить игроку только функции, которые ему действительно нужны.

Если игрок хочет создать изображение, он нажимает соответствующую кнопку. Выбор API-модели должен происходить автоматически по правилам приложения.

Если генерация временно недоступна, показывать понятное сообщение без технического стека ошибок.

## 4. Режим разработчика

Создать отдельную кнопку:

**«Разработчик»**

Желательно использовать небольшую тематическую иконку шестерёнки, ключа или щита.

Кнопка должна быть доступна из главного меню, предпочтительно в нижней части интерфейса, не конкурируя визуально с основными игровыми действиями.

При необходимости предусмотреть доступ к ней из меню приложения.

### 4.1. Проверка пароля

Начальный пароль:

`995539`

При нажатии открывается небольшое модальное окно:

**Доступ разработчика**

Поле ввода пароля с маскировкой символов.

Кнопки:

- «Войти»;
- «Отмена».

После успешной проверки открывается отдельная панель разработчика.

При неправильном вводе появляется сообщение:

«Неверный пароль».

Предусмотри ограничение повторных попыток, например временную задержку после нескольких ошибок.

Пароль не должен отображаться открытым текстом в настройках и пользовательских журналах.

Хранить локальный проверочный материал в форме, не требующей сохранения открытого пароля, и предусмотреть безопасную смену пароля владельцем.

**Важное ограничение:** фиксированный пароль внутри распространяемого EXE является только защитой интерфейса от случайного доступа. Его можно извлечь или обойти при анализе приложения.

Нельзя использовать пароль `995539` как замену серверной аутентификации или средство защиты реальных API-ключей.

### 4.2. Состояние авторизации

После успешного входа панель доступна в текущей сессии приложения.

Добавить кнопку «Выйти из режима разработчика».

После выхода технические разделы вновь блокируются.

При полном перезапуске игры доступ должен требовать повторной авторизации.

Не сохранять состояние авторизации в игровых сохранениях.

Проверять доступ не только при отображении кнопок, но и в обработчиках переходов к техническим страницам.

## 5. Структура панели разработчика

Панель должна выглядеть как единая административная консоль с тематическим оформлением DND-NCFU.

Рекомендуемые вкладки:

### 5.1. «ИИ-мастер»

Переместить сюда существующий функционал настройки мастера.

Сохранить:

- выбор API-провайдера;
- настройку модели;
- параметры генерации;
- технические системные инструкции;
- настройки контекста;
- параметры построения мира;
- тестирование соединения;
- отладочные ответы;
- диагностику;
- сведения о стоимости запросов.

Основная модель проекта сохраняется согласно действующим настройкам DeepSeek Flash.

Не менять модель автоматически при переносе настроек.

### 5.2. «ИИ-художник»

Перенести сюда существующие настройки генерации изображений.

Поддерживаемые модели:

`recraft/recraft-v4.1-flash`

`black-forest-labs/flux-3-image-klein`

Добавить отображение:

- выбранной модели для обычных предметов;
- модели для NPC и событий;
- стоимости;
- поддерживаемых разрешений;
- поддержки референсов;
- ограничений расходов;
- истории запросов;
- использования визуального кэша;
- состояния подключения.

Технические настройки доступны разработчику.

Обычный игрок видит только игровые действия: создать изображение, посмотреть, перегенерировать при наличии разрешения.

### 5.3. «Подключения»

Разместить:

- состояние RouterAI;
- режим подключения;
- настройки клиентского API для разработки;
- настройки серверного шлюза для тестовой версии;
- проверку доступности сервиса;
- сведения об авторизации;
- сообщения об ошибках.

Не смешивать MCP-токены Codex, административные ключи и API-ключи пользовательской игры.

### 5.4. «Бюджет и ограничения»

Отображать:

- расходы на текстовую генерацию;
- расходы на изображения;
- лимиты моделей;
- ограничения на пользователя;
- ограничения на генерацию новых миров;
- количество выполненных запросов;
- возможные ошибки тарификации;
- общие лимиты тестовой версии.

Настоящие финансовые ограничения общего тестового сервиса должны применяться сервером, а не только интерфейсом.

### 5.5. «Диагностика»

Включить:

- версию приложения;
- идентификатор сборки;
- версию базы данных;
- состояние игровых сохранений;
- состояние визуального реестра;
- проверку ресурсов;
- журналы ошибок;
- результаты безопасного self-check;
- проверку доступности серверного шлюза;
- экспорт диагностического отчёта без секретов.

### 5.6. «Управление тестированием»

Предусмотреть интерфейс для просмотра режима сборки, статуса тестового сервера и инструкций по управлению тестировщиками.

Если реализована серверная административная консоль, доступ к управлению тестировщиками должен дополнительно требовать реальной серверной авторизации.

Один лишь локальный пароль не должен давать полномочий изменять общий сервер или бюджет.

# ЧАСТЬ II. ИГРА, ГОТОВАЯ К ПЕРЕДАЧЕ ТЕСТИРОВЩИКАМ

## 6. Предварительно настроенные модели

При первом запуске обычный игрок не должен вручную:

- искать DeepSeek;
- выбирать RouterAI;
- указывать модели;
- копировать API-ключи;
- настраивать генераторы изображений;
- включать служебные переключатели;
- задавать системные промпты.

Эти параметры должны быть заранее настроены владельцем при подготовке тестового релиза.

Игроку остаётся:

1. Установить игру.
2. Запустить DND-NCFU.
3. Создать персонажа.
4. Указать пожелания к миру.
5. Начать приключение.

В рабочем режиме автоматически должны быть доступны ИИ-мастер и оба генератора изображений.

Это не означает автоматическую платную генерацию иллюстраций на каждом ходе.

Создание изображений остаётся явным действием игрока.

Если для запуска требуются внешние сервисы, игра должна проверять их доступность и корректно сообщать о проблемах.

---

## 7. Критически важная архитектура API для тестовой версии

Необходимо решить проблему распространения приложения, работающего с общим RouterAI-аккаунтом владельца.

**Запрещено встраивать действительный общий API-ключ RouterAI непосредственно в распространяемый EXE, установщик, ресурсы программы или файлы конфигурации.**

Локальное шифрование ключа не делает его безопасным для передачи другим пользователям: приложение должно иметь возможность его использовать, следовательно, технически подготовленный пользователь сможет исследовать этот механизм.

Пароль панели разработчика также не решает эту проблему.

### 7.1. Целевое решение — серверный API-шлюз

Разработай отдельный серверный компонент для тестовых сборок DND-NCFU.

Архитектура:

**Игра тестировщика → защищённый сервер DND-NCFU → RouterAI API → ответ игре.**

Настоящий API-ключ RouterAI находится исключительно на сервере владельца.

В клиентской игре его нет.

Сервер принимает запросы от авторизованных тестовых установок и обращается к утверждённым моделям.

Поддержать:

- текстовые запросы DeepSeek;
- генерацию изображений Recraft;
- генерацию изображений FLUX;
- передачу изображений-референсов;
- получение стоимости;
- обработку ошибок;
- ограничение расходов.

Не превращай сервер в новый игровой движок без необходимости. Сюжетная механика и постоянное состояние кампании могут оставаться в клиентском приложении, если это соответствует текущей архитектуре.

### 7.2. Обязательная защита сервера

Реализовать:

- HTTPS;
- авторизацию тестовых установок;
- индивидуальные отзывные права доступа;
- ограничение количества запросов;
- ограничение расходов;
- ограничения по моделям;
- ограничения по размеру запросов;
- защиту от бесконтрольных повторов;
- проверку форматов;
- таймауты;
- безопасные журналы;
- запрет произвольных запросов к неизвестным URL;
- запрет обращения к неутверждённым моделям;
- серверное хранение секретов;
- возможность немедленно отключить конкретного тестировщика.

Нельзя полагаться только на локальный счётчик расходов клиента.

### 7.3. Как обеспечить вход без ручной настройки

Для закрытого тестирования предусмотрите процедуру выпуска отдельного установщика или ограниченного клиентского допуска конкретному тестировщику.

Установка должна автоматически обращаться к тестовому серверу без необходимости выбора API-моделей.

Вариант первоначального допуска должен соответствовать возможностям выбранного хостинга.

Допускается индивидуальный ограниченный токен тестировщика или одноразовая предварительная активация, однако любое значение, находящееся внутри клиентского установщика, потенциально извлекаемо.

Поэтому такой токен не должен давать доступ к RouterAI напрямую или административные полномочия.

Его возможности должны ограничиваться сервером: небольшая квота, срок действия, отзыв и контроль расхода.

Не допускать анонимного неограниченного расходования общего баланса.

Не собирать скрытые идентификаторы оборудования и персональные данные ради привязки установки.

Если полностью автоматическое начало игры невозможно обеспечить безопасно при выбранном способе распространения, честно обозначь ограничение и предложи минимальную процедуру активации вместо небезопасного встраивания общего API-ключа.

### 7.4. Раздельные конфигурации сборок

Предусмотри два профиля:

**Developer Build**

Для владельца проекта.

Может использовать существующее защищённое хранение индивидуального API-ключа Windows.

Содержит все диагностические функции.

**Tester Build**

Для обычного игрока.

Работает через заранее настроенный серверный шлюз.

Не содержит общего ключа RouterAI.

Техническая конфигурация скрыта за панелью разработчика.

В обоих режимах пользовательские сохранения должны оставаться независимыми от файлов приложения.

### 7.5. Если сервер пока не развёрнут

Не выдавай клиентскую сборку с общим API-ключом как безопасную альтернативу.

Можно подготовить код шлюза, конфигурацию, тесты, документацию и установщик заранее.

Но не заявляй, что игра с облачным ИИ готова к полноценному тесту на чужом компьютере, пока сервер действительно не развёрнут и не проверен.

Не выполнять платных запросов и не арендовать сервер без моего разрешения.

Если появятся обязательные расходы на хостинг, сначала сообщи о них.

# ЧАСТЬ III. ПОЛНАЯ ПЕРЕРАБОТКА НАВИГАЦИИ

## 8. Убрать выпадающий список «Раздел»

Сейчас в верхней части игрового окна используется выпадающий список выбора раздела.

Он неудобен для обычного игрока и визуально делает интерфейс похожим на техническую программу.

Полностью заменить его горизонтальной панелью навигации.

### 8.1. Новая панель разделов

Использовать компактные тематические кнопки-вкладки, например:

**Приключение | Герой | Инвентарь | Задания | Энциклопедия | Фотоальбом | Меню**

Ориентироваться на реально реализованные разделы.

Не создавать пустые экраны с неработающими кнопками.

Дополнительные игровые разделы включать по мере их реализации.

Каждая вкладка должна быть кликабельной.

Активный раздел должен заметно выделяться.

### 8.2. Размещение

Панель располагается горизонтально под информацией о текущей сцене и состоянии героя.

По возможности занимает одну строку.

Не оставлять широкую пустую полосу, которая сейчас видна под навигацией на предоставленном скриншоте.

Использовать компактные отступы и единый размер кнопок.

При уменьшении окна:

- сначала сокращать отступы;
- затем при необходимости включать горизонтальную прокрутку панели;
- не допускать наложения кнопок;
- не переносить элементы хаотично;
- сохранять доступность клавиатурой.

### 8.3. Стиль вкладок

Визуальная тема:

- тёмно-синий и графитовый фон;
- бронзовые и золотистые контуры;
- тёплые светлые надписи;
- мягкое выделение выбранной вкладки;
- лаконичные тематические значки.

Навигация должна выглядеть как элемент фэнтезийной игры, а не стандартная форма настройки Windows.

### 8.4. Состояние экранов

Переключение разделов не должно:

- обнулять введённый текст;
- уничтожать состояние прокрутки;
- сбрасывать выбранный NPC;
- прерывать генерацию мира;
- запускать новый API-запрос;
- терять выбранный предмет;
- изменять текущее сохранение без необходимости.

# ЧАСТЬ IV. ЭНЦИКЛОПЕДИЯ ИГРОВОГО МИРА

## 9. Переименование «Хроник мира»

Переименовать пользовательский раздел:

**«Хроники мира» → «Энциклопедия мира»**

Это название яснее объясняет его назначение.

Внутри раздела можно сохранить художественный подзаголовок:

«Хроники забытых королевств».

Внутренние классы, ID и схему данных не обязательно переименовывать.

Важно сохранить совместимость существующих записей.

## 10. Новая структура энциклопедии

Сейчас категория выбирается через боковой список, а сведения отображаются в трёх колонках.

Нужно сделать более современный визуальный интерфейс.

В верхней части энциклопедии разместить горизонтальные категории:

**Все | Персонажи | Существа | Предметы | Места**

Дополнительные категории добавлять только при наличии соответствующей игровой информации.

При нажатии на категорию содержимое обновляется без перехода в отдельное окно приложения.

Под категориями разместить:

- поисковую строку;
- сортировку;
- фильтр известных сведений;
- сетку карточек.

### 10.1. Карточки энциклопедии

Вместо обычного вертикального списка объектов использовать сетку визуальных карточек.

Пример структуры карточки:

**Изображение объекта**

**Название**

Краткая категория или дополнительная информация.

Каждая карточка должна быть отдельной кликабельной областью.

Если изображение уже существует — загрузить его.

Если изображения нет — показать тематическую заглушку.

**Не выполнять платную генерацию автоматически при открытии энциклопедии.**

### 10.2. Открытие карточки

При нажатии на карточку открывать подробности.

Отображать:

- название;
- крупное изображение;
- описание;
- известные характеристики;
- последнюю встречу;
- связи с другими записями, если реализованы;
- доступные игроку заметки;
- действия с изображением.

Кнопки:

- «Посмотреть изображение»;
- «Создать изображение»;
- «Перегенерировать»;
- «Вернуться».

Кнопки, выполнение которых не имеет смысла или невозможно, должны корректно скрываться или отключаться.

### 10.3. Отображение описаний

Описание должно удобно читаться.

Не оставляй огромных пустых пергаментных панелей при коротком тексте.

Подстраивай расположение карточки под доступные данные.

Используй нормальные размеры шрифтов, интервал строк и достаточные поля.

Для длинных описаний — прокрутка.

Избегай чрезмерно мелкого текста.

### 10.4. Защита информации

Энциклопедия показывает только то, что знает герой.

Нельзя раскрывать:

- секретные мотивы NPC;
- будущие события;
- неизвестные свойства предметов;
- скрытые биографии;
- тайные локации;
- неопознанных врагов;
- внутренние планы мастера.

Используй существующую систему публичных знаний.

Не создавай второе, менее защищённое хранилище для нового интерфейса.

# ЧАСТЬ V. ОТДЕЛЬНЫЙ ФОТОАЛЬБОМ

## 11. Новый раздел «Фотоальбом»

Создать полноценный самостоятельный игровой раздел:

**«Фотоальбом»**

Его назначение — красивое хранение всех изображений, созданных во время приключения.

Это не технический каталог JSON и не интерфейс настройки моделей.

Фотоальбом должен восприниматься как альбом воспоминаний героя.

### 11.1. Содержание

Показывать изображения:

- героя, если создан портрет;
- NPC;
- монстров и существ;
- предметов;
- локаций;
- событий;
- сражений;
- памятных моментов.

Каждое изображение должно сопровождаться названием и кратким описанием.

### 11.2. Дизайн фотоальбома

Использовать сетку изображений с адаптивным количеством колонок.

Фотографии отображать в аккуратных карточках.

На карточке:

- миниатюра;
- название;
- категория;
- краткое описание или дата события.

Например:

**Встреча в Отмели Семи Вёсел**

«Асуна впервые поговорила с Керрой у старой пристани».

Это пример представления данных, а не заранее заданный сюжет.

Настоящий текст брать из текущей кампании.

### 11.3. Открытие изображения

При нажатии на миниатюру открывать увеличенное изображение.

В окне просмотра:

- крупная картинка;
- название;
- описание;
- связь с объектом или событием;
- кнопка закрытия;
- переход к предыдущему или следующему изображению.

Предусмотри возможность открыть исходную запись энциклопедии или журнала.

Опционально добавить сохранение изображения в выбранное пользователем место на компьютере.

### 11.4. Категории фотоальбома

Сделать горизонтальную панель:

**Все | Персонажи | Существа | Предметы | Локации | События**

Категории должны работать с существующим реестром изображений.

Не создавать копии изображений только ради сортировки.

### 11.5. Работа с версиями

Если изображение объекта несколько раз перегенерировалось:

- по умолчанию показывать утверждённый вариант;
- дать возможность просматривать прошлые версии;
- не удалять старые версии автоматически;
- не терять изображения, на которые ссылаются сюжетные сцены.

### 11.6. Пустой фотоальбом

Если изображений пока нет, показывать красивое пустое состояние.

Например:

«Ваша история только начинается. Когда появятся первые иллюстрации, они сохранятся здесь».

Добавить понятную ссылку на игровой экран или энциклопедию.

Не запускать платную генерацию ради заполнения пустого альбома.

### 11.7. Изоляция кампаний

Альбом должен отображать только изображения текущей кампании.

При переключении сохранения содержимое обновляется.

Никакие картинки из чужой кампании не должны появляться случайно.

# ЧАСТЬ VI. АНИМАЦИИ И ВИЗУАЛЬНАЯ ПОЛИРОВКА

## 12. Единая система анимаций

Сейчас интерфейс работает, но выглядит сравнительно статичным.

Нужно придать ему визуальную плавность и ощущение полноценной RPG.

Не используй случайные эффекты на каждой кнопке.

Разработай общую систему анимаций интерфейса с едиными параметрами и стилем.

Используй штатные возможности PySide6/Qt:

- `QPropertyAnimation`;
- `QParallelAnimationGroup`;
- `QSequentialAnimationGroup`;
- `QEasingCurve`;
- `QGraphicsOpacityEffect`;
- другие подходящие средства Qt.

Учитывай, что отдельные свойства виджетов могут требовать специальных способов анимации.

Не анимировать тяжёлые виджеты таким способом, который создаёт постоянную избыточную нагрузку.

### 12.1. Анимации кнопок

Для интерактивных кнопок:

**Наведение:** лёгкое изменение яркости, цвета рамки или фона.

**Нажатие:** короткая визуальная реакция.

**Выбранная кнопка:** устойчивое золотистое выделение.

**Недоступная кнопка:** визуально понятное неактивное состояние.

Не допускать сильных подпрыгиваний и постоянной пульсации.

### 12.2. Переключение разделов

При переходе между разделами:

- плавное появление содержимого;
- лёгкая смена прозрачности;
- небольшое перемещение, если это не нарушает компоновку.

Рекомендуемая длительность обычного перехода: примерно 150–250 мс.

Анимации не должны задерживать обработку пользовательских действий.

### 12.3. Карточки объектов

Карточки должны реагировать на наведение:

- мягкое выделение рамки;
- изменение фона;
- появление визуального акцента.

При открытии подробной карточки — плавный переход.

При закрытии — короткая обратная анимация.

Клик должен работать и во время завершения анимации.

### 12.4. Фотоальбом

При появлении сетки изображений можно использовать мягкое последовательное проявление видимых карточек.

При открытии фотографии:

- фон затемняется;
- изображение плавно появляется;
- подписи становятся видимыми.

Не выполнять тяжёлое одновременное масштабирование десятков полноразмерных фотографий.

### 12.5. Уведомления

Добавить единый стиль уведомлений для:

- успешного сохранения;
- получения изображения;
- завершения генерации;
- ошибок сети;
- завершения создания мира;
- превышения игрового лимита.

Уведомление должно аккуратно появляться и исчезать.

Важные ошибки не должны исчезать прежде, чем пользователь успеет их прочитать.

### 12.6. Настройки анимаций

В обычных настройках игрока добавить:

- включение и отключение анимаций;
- уменьшение интенсивности эффектов;
- при необходимости выбор производительного режима.

Учитывать системную настройку уменьшения анимаций, если платформа предоставляет её приложению.

Все важные функции должны оставаться доступными без анимаций.

### 12.7. Производительность

Игра должна комфортно работать на Windows-компьютерах с интегрированной графикой.

Не использовать тяжёлые видеофоны в каждом разделе.

Не выполнять постоянную перерисовку невидимых экранов.

Не замедлять ИИ-мастера, ввод текста или генерацию изображений визуальными эффектами.

Не допускать мерцания, утечек памяти и накапливающихся обработчиков анимаций.

# ЧАСТЬ IX. ТЕСТИРОВАНИЕ

## 17. Автоматические проверки

Создай или обнови тесты для следующих сценариев.

### Режим разработчика

- Без пароля нельзя открыть техническую панель через интерфейс.
- Неверный пароль отклоняется.
- Правильный пароль открывает панель.
- После выхода доступ закрывается.
- После перезапуска требуется новый вход.
- Прямые переходы к закрытым страницам проверяют доступ.
- API-ключи не появляются в логах или пользовательских файлах.

### Игровой режим

- Создание персонажа работает.
- Создание мира работает.
- Приключение запускается.
- Технические настройки не видны.
- Настройки мастера и художника не требуются игроку для обычного запуска.
- Навигация не теряет состояние.

### Энциклопедия

- Горизонтальные категории работают.
- Поиск работает.
- Фильтры работают.
- Карточки открываются.
- Изображения соответствуют объектам.
- Секреты мира не раскрываются.
- Отсутствие изображения не вызывает платный API-запрос.

### Фотоальбом

- Изображения загружаются из существующего реестра.
- Названия и описания соответствуют объектам и событиям.
- Полноразмерный просмотр работает.
- Переключение кампании очищает отображение предыдущей.
- Перезапуск сохраняет изображения.
- Прошлые версии не теряются.

### Анимации

- Переходы не блокируют интерфейс.
- Выключение анимаций работает.
- Нет накопления бесконечных таймеров.
- Переход во время активного эффекта не приводит к ошибке.
- Работа с клавиатуры сохраняется.

### Серверное подключение

- Игра не содержит общего RouterAI API-ключа.
- Неавторизованный запрос отклоняется.
- Истёкший или отозванный доступ блокируется.
- Серверные лимиты применяются независимо от клиента.
- Нельзя выбрать произвольную дорогую модель через подмену запроса.
- Ошибки сервера корректно отображаются.
- Общий бюджет не может обходиться через изменение локальных файлов.
- При недоступности сервера локальная игра не повреждается.

# ЧАСТЬ X. ПОРЯДОК РАЗРАБОТКИ

## 19. Этапы реализации

Реализуй последовательно.

**Этап 1. Аудит.**

Изучить актуальную архитектуру, интерфейс, изображения, настройки, сборку и финансовые ограничения.

**Этап 3. Перенос технических настроек.**
