# База мира: подключение мастера и обучение

Библиотеку подключают **до подготовки обучающих примеров**. Ею можно пользоваться
с уже установленной моделью: дообучение для поиска карточек не требуется.
Если модель уже обучена, подключение выполняется теми же командами. Новые предметы
и исправления описаний добавляются в библиотеку без повторного обучения весов.

## Быстрый запуск на Windows

Распакуйте выпуск в новую папку. В нём `source` — исходный проект,
`DND-NCFU-master-library.sqlite3` — глобальная библиотека, а не сохранение партии.
Нужны Python 3.12 и зависимости проекта. Установка из `source`:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --require-hashes -r requirements-dev.lock
```

Если проект и окружение уже установлены, используйте их; создавать новое окружение
не обязательно. В существующем checkout обновление этой ветки:

```powershell
Set-Location D:\Projects\DND-NCFU
git fetch origin
git switch codex/structured-world-catalog-20261105
git pull --ff-only
```

При локальных несохранённых правках сначала сохраните их обычным способом.
Далее из корня проекта, указав фактический путь к распакованной базе:

```powershell
$catalogPath = 'D:\DND-NCFU-release\DND-NCFU-master-library.sqlite3'
.\.venv\Scripts\python.exe scripts\world_master.py --db $catalogPath doctor
.\.venv\Scripts\python.exe scripts\world_master.py --db $catalogPath context 'короткий лук'
.\.venv\Scripts\python.exe scripts\world_master.py --db $catalogPath run
```

Ожидается `READY_FOR_LOCAL_RETRIEVAL`, `records: 27426`, `database_access: read-only`;
вторая команда выводит до трёх карточек с ID, редакцией и digest. Третья открывает
обычную игру с подключённым каталогом. Она не скачивает модель и не меняет её настройки.
В игре выберите уже установленную локальную модель в настройках рассказчика.
Без LLM числовой движок и отдельное окно библиотеки продолжают работать локально.
Ошибку недоступной модели исправляют в её настройках; каталог сам модель не запускает.

Просмотр, импорт, предложения новых шаблонов и создание в копии мира:

```powershell
.\.venv\Scripts\python.exe scripts\world_library_ui.py $catalogPath
```

Первая вкладка показывает карточку для мастера, вторая — все поля и происхождение.
Шаблон не означает, что существо уже присутствует в сцене. Поиск и просмотр не меняют
мир. Для независимого запуска игры вручную можно задать переменную только текущего
PowerShell: `$env:RPG_VKR_WORLD_LIBRARY = $catalogPath`, затем запустить
`scripts\run_game.py`. Удаление этой переменной отключает новое извлечение контекста.

## Как пользоваться в партии

1. Найдите предмет или NPC в библиотеке и скопируйте его устойчивый ID.
2. В чате мастера попросите: `Создай рядом <ID>`. Модель получает ограниченную карточку
   и предлагает `library_requests` с этим ID, редакцией, digest и новым ID экземпляра.
3. Движок заново проверяет шаблон, зависимости, схему и текущую сцену. Перед созданием
   окно показывает конкретное предложение. Отказ не создаёт сущности и не бросает кубики.
4. Новый предмет появляется в сцене. Он не выдаётся герою автоматически: подобрать,
   купить, украсть или получить его можно только обычным действием движка.
5. При `with_inventory=true` начальное имущество NPC создаётся реальными экземплярами,
   принадлежащими NPC. Его оружие изнашивается; отсутствующее оружие не появляется вновь.

Модель может ошибиться с JSON или не предложить создание. В этом случае операция
отклоняется; тот же экземпляр можно создать через окно библиотеки в **новой SQLite-копии**
штатного экспорта мира. Старый файл не перезаписывается. Точный CLI:

```powershell
.\.venv\Scripts\python.exe scripts\world_library.py --db $catalogPath instantiate wl_npc_0_0 smith_01 .\world-export.sqlite3 .\world-with-smith.sqlite3 --with-inventory
```

`world-export.sqlite3` здесь — экспорт кампании из игры, а не файл глобального каталога
и не JSON-ячейка сохранения. Созданную копию открывают штатным импортом SQLite-кампании.
Если мир закрепил прежнюю редакцию шаблона, явный `--new-revision` создаёт отдельное
определение для нового экземпляра. Старые экземпляры сохраняют прежние свойства.

Для принадлежащих герою экземпляров мастер получает допустимые команды в
`catalog_actions.library_items`. Формула: `library_magic`; рецепт: `library_recipe`;
еда, лекарство, вымышленный яд, книга или квестовая вещь: `library_use`.
Команда содержит **ID экземпляра**, а не глобальный ID шаблона. Например:

```json
{"steps":[],"places":[],"check":"none","gameplay":{"command":"library_use","args":{"item":"my_dressing","target":"wounded_npc"}}}
```

HP, MP, ST, деньги, предметы, время, урон и RNG рассчитывает Python. Рассказчик пишет
по результату квитанции. R01–R14 остаются правилами движка. Обычное лечение не воскрешает
мёртвого; еда расходует одну порцию и проверяет срок хранения; яд — только вымышленная
боевая механика; чтение и осмотр не выдают произвольные XP, деньги или награду.
Не всякая справочная строка имеет обработчик: `mechanics.version=descriptive`
означает справку. Неподдержанные исходные особенности видны отдельно и не исполняются
по обещанию модели. Фактическое покрытие: `data/world_library/runtime-coverage.json`.

## Шаблоны, экземпляры и PostgreSQL

Глобальный шаблон хранит происхождение, неизменяемую редакцию, типизированные
атрибуты и закреплённые версии компонентов. Экземпляр мира хранит владельца, положение,
количество и текущее состояние. Один глобальный ID можно использовать в разных мирах
с разными состояниями. Новое описание шаблона не лечит уже раненого NPC.

Новый авторский шаблон сначала проходит `Library.propose`: закрытую схему профиля,
пределы баланса, уникальность и ссылки. `Library.approve` сохраняет одобренную редакцию
в транзакции с аудитом. Исполняемые эффекты задаются кодом версионированного обработчика,
а не Python/SQL из ответа LLM. Создание экземпляров использует `preview` → валидацию →
`Session.register_catalog`; журнал Session позволяет проверить результат и replay.

PostgreSQL — дополнительное хранилище библиотеки и архивных проекций. Работающая
партия по-прежнему сохраняется существующим SQLite/JSON-механизмом. Для PostgreSQL
используйте отдельную локальную БД, `DND_LIBRARY_DSN` и инструкции
[WORLD_LIBRARY.md](WORLD_LIBRARY.md). Мастер читает локальное SQLite-зеркало: экспорт
из PostgreSQL через `world_library.py --postgres export`, затем импорт JSONL в новую
локальную библиотеку. Не подставляйте PostgreSQL DSN в `RPG_VKR_WORLD_LIBRARY`.
Пользовательские сохранения не мигрируют автоматически.

## Что обучать

JSONL каталога — база знаний, а не готовые пары SFT. Для обучения мастера нужны пары:
проверенный контекст сцены + полученные карточки + предложение действия либо квитанция
движка → правильный JSON либо литературное описание **уже рассчитанного** результата.
Не обучайте модель произвольно изменять HP, выдавать предметы или вычислять RNG.
Каталог извлекается при игре независимо от того, какое описание попало в веса модели.

В проекте уже есть отдельный синтетический narrator-корпус V4: 1100 примеров,
880 train / 110 validation / 110 test. Это авторские синтетические сценарии,
не реальные партии и не 27 426 обучающих диалогов. Ручных построчных оценок — 0.
Вариант FIREBALL содержит 1196 примеров и отдельную политику допуска; его нельзя
незаметно смешивать с основным экспериментом. Описание и готовые команды —
[TRAINING_DATA_V4.md](intelligent_gm/TRAINING_DATA_V4.md) и
[QLORA_DATA_READY.md](intelligent_gm/QLORA_DATA_READY.md).

Приватный корпус и оригинальные веса не включаются в исходный Git-архив. Если прежнего
приватного корпуса нет, можно воспроизвести **кандидат** и его автоматический аудит:

```powershell
.\.venv\Scripts\python.exe -m training.grounded_curriculum --output .\data\local-v4-candidate
.\.venv\Scripts\python.exe -m training.grounded_validation --directory .\data\local-v4-candidate --output .\local-v4-audit.json
```

Это ещё не допущенный корпус: для допуска нужны сохранённые реальные решения владельца
по синтетическим состояниям (`--owner-decisions`), затем точная токенизация закреплённым
токенизатором и связанный CPU-отчёт. Нельзя подделывать `DIRECT_USER_REPLY` или менять
статус manifest вручную. При `BLOCKED_DATA` сначала устраняют указанную причину.
Новый протокол создания из библиотеки можно использовать через runtime-инструкцию
без изменения прежнего корпуса; отдельный SFT этого протокола здесь не заявляется.

При дополнении корпуса разделяйте целые кампании, семейства исходных существ и
варианты одного шаблона между train/validation/test. Сначала дедупликация, затем split;
региональные перекраски и копии одного источника не должны утекать в test.
Для ручной оценки проведите пилот 30–50 примеров с независимыми разметчиками,
посчитайте их согласие и сохраните ID разметчика, версию промпта/движка/модели и время.
Не объявляйте эту работу уже выполненной по одному автоматически собранному PDF.

## Дополнительное QLoRA-обучение без аренды и платного API

Этот путь рассчитан на собственный, предоставленный другом или университетский
Linux/WSL2-компьютер с NVIDIA CUDA и BF16. 24 GiB VRAM — ориентир, а не обещание
вместимости. На ноутбуке с Iris Xe этот конкретный QLoRA-конвейер не запускается;
готовая локальная модель с каталогом может работать без обучения.
QLoRA обучает адаптер поверх квантованной базы; это соответствует
[документации PEFT](https://huggingface.co/docs/peft/developer_guides/quantization).

Из корня проекта задайте пути к **уже допущенному** корпусу и его CPU-отчёту:

```powershell
$datasetPath = 'D:\DND-NCFU-data\gm-grounded-synthetic-v1'
$cpuReportPath = Join-Path $datasetPath 'cpu-tokenization.json'
.\.venv\Scripts\python.exe -m training.prepare_faun_transfer --dataset $datasetPath --grounded-synthetic --cpu-report $cpuReportPath --output .\faun-local-transfer.zip
```

Архив tools-only: отдельно перенесите корпус и неизменённый CPU-отчёт на GPU-машину
в `data/processed/gm-grounded-synthetic-v1`. Распакуйте tools в новую папку.
Получатся `faun-smoke.json` и `faun-full.json` с привязкой к хэшу данных.
На GPU-машине:

```bash
python3.12 -m training.check_faun_data --config faun-smoke.json --output integrity-001.json
python3.12 -m training.hardware_preflight --scope friend_gpu --output hardware-001.json
python3.12 -m training.setup_faun_gpu --install-stack
python3.12 -m training.setup_faun_gpu --download-base
.venv-faun/bin/python -m training.train_lora --config faun-smoke.json --dry-run
.venv-faun/bin/python -m training.train_lora --config faun-smoke.json --smoke-test
```

Установка и загрузка — явные отдельные команды с подтверждением объёма; оригинальные
Safetensors занимают около 24 GB. GGUF для игры не является их заменой в этом конвейере.
База закреплена: `limloop/MN-12B-Faun-RP-RU` на ревизии
`bdfc761b14feb9dd03ef158a4d337fc1cf5fd183`. Проверка не скачивает веса неявно.
Только после двух реальных smoke-шагов, конечного loss и проверки загрузки адаптера:

```bash
.venv-faun/bin/python -m training.train_lora --config faun-full.json
```

Параметры: NF4, BF16, LoRA rank 8, q/k/v/o, batch 1, accumulation 16,
max_length 2048, одна эпоха. Test не участвует в градиентах. Время и качество нужно
измерять на фактическом оборудовании. Эти команды в данном выпуске не запускали обучение.

## Проверка и подключение после обучения

На той же GPU-машине запустите базу без адаптера, затем после её остановки — с адаптером.
Оценку выполняйте в другом терминале с одним и тем же корпусом:

```bash
.venv-faun/bin/python -m training.serve --config faun-full.json --baseline --port 11435
.venv-faun/bin/python -m training.evaluate_faun --directory data/processed/gm-grounded-synthetic-v1 --grounded-synthetic --run-local --port 11435 --model dnd-base-narrator --limit 110 --output base-test.json
```

```bash
.venv-faun/bin/python -m training.serve --config faun-full.json --adapter artifacts/faun-full --port 11435
.venv-faun/bin/python -m training.evaluate_faun --directory data/processed/gm-grounded-synthetic-v1 --grounded-synthetic --run-local --port 11435 --model dnd-trained-narrator --limit 110 --output trained-test.json
.venv-faun/bin/python -m training.compare_models --run base-test.json --run trained-test.json --output comparison.json
```

Нужны также просмотр человеком и реальные сценарии игры, особенно создание по ID,
отказы, нехватка MP/предметов и сохранение/replay. `training.export_model` требует
реальный адаптер и положительное решение владельца по holdout; автоматического
одобрения за пользователя нет. Сервер `training.serve` слушает localhost.

Для ноутбука предусмотрен `training.merge_gguf`: после одобренного deployment manifest
он объединяет адаптер с **той же** базой и через локальный llama.cpp создаёт Q4_K_M.
Сначала проверяют его план без `--execute`; точные параметры выводит `--help`.
Это требует дополнительной RAM/диска. Готовый файл импортируют в Ollama через Modelfile
с `FROM ./model-Q4_K_M.gguf`, затем `ollama create dnd-trained-local -f Modelfile`.
Формат импорта описан в [документации Ollama](https://docs.ollama.com/import).
Проверьте качество после квантования и выберите новую модель в игре отдельным именем.
Прежнюю модель сохраните для сравнения. Обучение не гарантирует ускорения на CPU.

Запуск с каталогом остаётся тем же: `world_master.py --db <путь> run`.
Переобучение не меняет права LLM: шаблоны поступают из базы, изменения состояния —
только через предложения, проверку и транзакции Python-движка.
